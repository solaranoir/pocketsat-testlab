# Golden telemetry captures (#64)

Each `.golden` file holds **every downlink frame** a scenario produces on `SilTarget` for
one seed, byte for byte. `tests/sil/test_golden_telemetry.py` regenerates each capture
from the seed recorded in its header and compares the frames, tick and bytes; a
failure names the first differing frame, its tick and time, the differing byte offsets,
and both frames' decoded fields (header, telemetry, ACK, or DATA), marking the fields
that differ.

ADR-0006 makes SIL arithmetic portable, so a capture generated on any platform is
byte-identical on every other; CI runs the comparison on Linux and macOS.

| Capture | Scenario | Frames | Size | Suite |
|---|---|---|---|---|
| `nominal_seed42.golden` | #63's nominal scenario, seed 42: boot, PING, SET_MODE SCIENCE, one 10-minute DOWNLINK pass at the end of a 92-minute orbit (#72's reference profile), SET_MODE NOMINAL, then 2 s in NOMINAL; 55,220 ticks | 8,499 | about 1.1 MB | slow (regenerating takes about 4 s) |
| `sensor_freeze_seed42.golden` | The same start, then `sensor_freeze` on every sensor at 200 s for 20 s, while the payload acquires; 2,300 ticks | 228 | about 22 kB | fast |

The nominal capture is generated by #63's nominal scenario harness,
`run_nominal_scenario` in `tests/sil/_nominal_scenario.py`; the `sensor_freeze` capture
uses the same command times.

## Format

UTF-8 text with LF line endings (`.gitattributes`). A header of `# key: value` lines,
then one line per frame in the order `receive()` returned them:

```
<tick> <time_s> <TYPE> <frame hex>
49 5.000 TELEMETRY a55a01020000001a0000138800000000010201001c2701f707c707b400000000137fc788
50 5.100 ACK a55a01030001000400010100965e
```

- `tick`: counted from 0, the first `advance()` after `reset(seed)`.
- `time_s`: simulated time at the **end** of the tick, the instant the flight
  computer's readings describe.
- `TYPE`: the frame type from the header byte, for reading only (checked on load).
- `frame hex`: the whole wire frame, sync to CRC (`docs/protocol.md`).

The header records the scenario, its seed, the tick, the number of ticks, the orbit,
the settings by name (`NOMINAL_CONFIG`, `DEFAULT_INITIAL_STATE`,
`DEFAULT_FLIGHT_COMPUTER_CONFIG`), the protocol version, the frame count, and
`frames_sha256` (each frame's tick as uint32 big-endian, its length as uint16
big-endian, then its bytes, the scheme of `tests/sil/test_behavior_digests.py`). One
line per frame keeps a change reviewable: a diff shows which frames changed and when.

**Size.** The nominal capture is one hex line per frame for a whole orbit: 5,519
telemetry frames (36 bytes each), 2,976 DATA frames (78 bytes) and 4 ACKs, 431 kB of
wire bytes, about 1.1 MB as text (git stores it compressed). #64 asks for a byte-for-byte
comparison of the nominal scenario, which runs for a full orbit (#63), so the bytes are
kept in full rather than as a digest.

## Regenerating

```
uv run python tests/sil/_golden.py --check                       # compare, write nothing
uv run python tests/sil/_golden.py --regenerate                  # rewrite every capture
uv run python tests/sil/_golden.py --regenerate nominal_seed42   # rewrite one
```

Regenerating is **deliberate**, never a way to make a failing test pass. A golden
change goes in its own commit, with the PR saying why the bytes changed and what the
first difference was (run `--check` before regenerating, and paste its report). It is
allowed only for:

- **A protocol change**: a new or changed frame or payload layout, with the protocol
  version change and ADR `docs/protocol.md` requires.
- **A change to the within-tick order or latencies**, ADR-0003 §2 and ADR-0004 §2,
  which only a **new ADR** may make; the PR links that ADR.
- **A deliberate change to a model, a default setting, the starting state, the
  flight software's behaviour, or the scenario**, reviewed as such (for example a
  recalibration).

Anything else that changes the bytes is a regression: a speed-up, a refactor, or a
change meant to keep behaviour at the 100 ms tick (for example #122, comms capacity as
a rate) must leave the captures unchanged. The bytes contain reported values, so they
include seeded sensor noise (and, in the fault capture, frozen readings); they are
expected to be identical for a given seed, so a noise difference is a real change too.
